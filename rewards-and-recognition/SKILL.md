# 奖励与认可 (Rewards and Recognition)

## R — 核心要旨 (Reading)

在建立精心设计的奖励认可计划之前, 先搞清楚什么对员工真正管用。管理者常坚信自己知道员工要什么, 但除非去问员工本人, 否则无从真正了解——可以做焦点小组, 或问一群有代表性的员工。

---

## I — 方法论骨架 (Interpretation)

这条方法论回答一个反直觉的问题: 你怎么知道员工想要什么奖励? 答案不是问领导层, 而是去问员工本人。做法分三步:

1. **先问后设** — 设计前先做调查: 召集覆盖不同年龄段、性别、层级、种族的代表性焦点小组, 由受过训练的主持人引导, 现场不承诺任何东西, 让员工说出真正能打动他们的认可形式。
2. **筛选** — 从建议里挑出同时满足"符合组织价值观"和"在预算内"的选项, 别照搬预算表或别人家的方案。
3. **匹配** — 奖励要对上"人"和"成就": 有人喜欢当众表扬, 有人更愿意被安静地肯定, 一刀切的表彰大会会适得其反。

另有一条顺序铁律: 领导软弱、工作环境消极时, 奖励救不了场——先修地基 (领导力+环境), 再谈激励设计。

---

## A1 — 应用案例 (Past Application)

### 案例 1: 领导层想设"每月最佳员工现金奖"
- **问题**: 高管自信"员工最想要的就是现金奖", 准备直接拍板设奖。
- **方法论的使用**: 方法主张别信领导层的猜想——高管想要的往往不是员工需要的; 用代表性焦点小组去问员工真正有效的认可形式。
- **结论**: 设计顺序是"先问后设", 不是"先设再问"; 领导层的意见只能当待验证的假设。
- **结果**: 从员工建议中筛出符合价值观且符合预算的方案, 而非照搬现金奖。

### 案例 2: 给内向技术大牛办全员表彰大会
- **问题**: 组织默认"公开表扬对谁都有效", 打算大张旗鼓表彰一位技术骨干。
- **方法论的使用**: 奖励要匹配"人"与"成就"——有些人并不喜欢当众被表扬, 更愿被安静地认可。
- **结论**: 公开表扬对多数人有效, 但有一类人对当众表彰是负体验; 大张旗鼓之前先探明对象偏好。
- **结果**: 对这类员工改为私下、安静、针对具体事项的肯定, 效果优于全员大会。

### 案例 3: 团队氛围差、领导软弱, 想用花样激励救场
- **问题**: 团队士气低、主管不管下属, 有人提议"搞个有意思的激励活动"救场。
- **方法论的使用**: 方法强调强激励救不了坏领导——没有强领导力和积极的工作环境, 奖励再多也无效。
- **结论**: 顺序原则是先修领导力与环境, 再谈激励设计; 顺序反了, 激励投入全白费。
- **结果**: 把预算和注意力先放到改善管理与工作环境上, 而非用奖励掩盖根因。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想设计或改革奖励/认可计划 (月度之星、现金奖、纪念品、感谢信、年度颁奖)
2. 花了钱做激励却没效果, 或员工对现有奖励形式反应冷淡
3. 高管拍板"员工最想要 X", 但你想验证真实需求而不是拍脑袋
4. 预算有限, 想要零成本/低成本认可方案 (真诚的"谢谢"、午餐会、公开致谢)
5. 新管理者想尽快"让团队感到被认可", 不知道从哪下手

### 语言信号 (用户的话里出现这些就应激活)

- "奖励计划" / "认可员工" / "月度之星" / "颁奖" / "表扬员工" / "激励方案" / "员工想要什么奖励"
- "rewards program" / "recognition" / "employee of the month" / "award" / "how to appreciate staff" / "how to motivate my team"

### 与相邻 skill 的区分

- 与 `compensation-and-pay-equity` 的区别: 该 skill 管"给多少钱" (薪资结构、带宽、同工同酬审计); 本 skill 管"钱以外的认可" (低成本、真诚感谢、对人对事匹配)。一旦进入薪资数字/带宽/审计, 转走。
- 与 `employee-experience-and-retention` 的区别: 该 skill 管敬业度测量、留任归因与流失成本; 本 skill 只负责"认可/奖励"这一个激励杠杆的设计, 是敬业度的驱动因素之一, 不是测量本身。
- 与 `benefits-and-leave` 的区别: 福利是制度性的间接回报 (保险/休假, 有法律边界); 本 skill 是非现金、低成本的即时认可, 无法律门槛。

---

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **先问员工, 不臆断**
   - 完成标准: 完成 ≥1 组覆盖代际/层级/性别代表样本的焦点小组或抽样访谈; 产出原始"员工想要的认可形式"清单; 领导层的意见被显式标记为"待验证假设"而非既定结论。

2. **筛选与匹配 (价值观 + 预算 + 对象偏好)**
   - 完成标准: 每条候选建议都标注"匹配的组织价值观 + 预算档位 + 适用人群 (谁喜欢公开 / 谁喜欢私下)"; 形成一页设计草案, 明确每项奖励对应的"人"与"成就"。
   - 判停条件: 若诊断出团队领导软弱或工作环境消极 → 跳到步骤 3 的"先修地基"部分, 不启动奖励计划 (奖励救不了坏领导)。

3. **落地程序 + 度量**
   - 完成标准: 程序写明"谁提名 / 何时颁发 / 如何颁发 / 谁负责维护"; 设 90 天回顾机制与成功度量 (参与率、使用率、员工反馈信号); 零成本方案 (针对具体事项的真诚"谢谢") 已纳入。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯信息查询 ("什么是员工认可") — 无决策情境, 不该激活。
- 谈薪资结构、带宽、同工同酬审计 — 那是 compensation-and-pay-equity 的领域。
- 员工诉求本质是"要加钱" — 钱的问题走薪酬流程, 认可设计补不上现金差距 (参考 Pink 三动机: 先把钱付到"让钱下桌")。

### 常见失败模式

- 领导层自以为是地设计奖励 (高管想要的 ≠ 员工需要的), 不先问员工。
- 公开表扬一刀切 — 有人不喜欢当众被表扬, 要匹配"人"与"成就"。
- 靠奖励/激励修补坏领导与消极环境 — 顺序反了, 投入全白费。
- 设计程序喧宾夺主 — 流程比"人的感受"重要, 是常见走偏。

### 方法论局限 / 适用边界

- 整体为美国语境, 部分奖励/认可惯例与当地文化、法律 (如应税奖励) 相关, 需本地化。
- 假设组织有成型的 HR 部门、预算与体系支撑 — 对无 HR 的小团队是空中楼阁。
- 代际本质主义: 把千禧一代当作需要"特殊管理方法"的独特物种, 这类刻板印象如今广受批评。
- 方法论与案例自引的 Gallup 研究存在张力: 流程化的奖励程序是骨架, 信任与优势导向的领导力才是血肉。

### 容易混淆的邻近方法论

- **总回报模型 (total rewards)**: 认可只是总回报中"非现金"的一环, 别把它当成员工回报的全部。
- **Pink 内在动机三要素 (Autonomy/Mastery/Purpose)**: 这是留任/激励的另一个框架; 认可设计是其中"目的感"的具体落地, 但两者不是同一件事。

## 快速理解: 5 个示例问题

用这 5 个最常被问到的场景快速上手本 skill, 每个问题都对应它真正触发的处理动作:

1. **想设'每月最佳员工'现金奖, 但不确定员工到底想要什么奖励。** — 先问后设: 焦点小组代替领导拍板
2. **花了钱做激励计划, 员工却反应冷淡, 为什么?** — 复盘奖励与'人'与'成就'的匹配
3. **预算为零, 怎么低成本认可员工?** — 零成本认可方案 (真诚感谢/午餐会/公开致谢)
4. **要给一位内向的技术大牛办全员表彰大会, 合适吗?** — 奖励匹配对象偏好: 改私下认可
5. **团队氛围差、主管软弱不管事, 有人提议搞激励活动救场。** — 判停: 奖励救不了坏领导, 先修领导力
