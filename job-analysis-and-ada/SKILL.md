# 职位分析与合理便利 (Job Analysis & ADA)

## R — 核心要旨 (Reading)

职位分析是对职位的系统研究: 确定岗位包含的活动与职责、相对重要性、任职所需资格, 以及工作是在何种条件下进行的。关键事实: 分析的对象是职位本身, 而不是任职者。

---

## I — 方法论骨架 (Interpretation)

职位分析是先于"人"的分析: 系统研究一个岗位包含的活动与职责、相对重要性、任职所需知识/技能/能力 (KSA)、工作条件, 产出职位描述与职位规范。关键原则是**分析职位而非任职者**——即使数据从在职者收集, 也不能按某个人的做法定义岗位, 否则会"按人定岗", 破坏招聘、薪酬与绩效的公平。职位描述是招聘、定级、绩效、ADA 合规共同的地基, 每条关于"核心职能"的说法都要能拿出证据, 因为会被联邦合规机构审查。

在 ADA 语境下, 职位描述中的 essential functions (核心职能) 决定雇主的合理便利义务: 合理便利是移除阻碍、让合格残障者履行核心职能的调整(改工时、岗位重组、调至空缺岗、改装设备)。处理流程是**逐案互动**——记录所有请求、逐一评估、与员工本人协商、文档化全过程; 但不必采用员工首选方案, 也不得删除核心职能或降低标准; 只有构成 undue hardship (过度负担, 相对企业规模的逐案判断) 才能拒绝。

## A1 — 应用案例 (Past Application)

### 案例 1: Griggs v. Duke Power (职位分析缺失的代价)
- **问题**: 公司以"高中文凭 + 两项预录用测试"为录用/晋升门槛, 却从未做职位分析、无法界定这些要求与岗位核心职能的关系。
- **方法论的使用**: 职位分析缺失 → essential functions 无法界定 → 筛选要求"与工作无关"——这正是"职位先于人"的可辩护性反面。
- **结论**: 对"岗位到底要什么"拿不出证据的雇主, 其筛选要求经不起审查。
- **结果**: 最高法院认定要求与工作无关且产生排他效果, 构成歧视——职位分析是地基的判例级证明。

### 案例 2: 职位分析访谈问题样张 (方法提供的采集工具)
- **问题**: 要为岗位收集准确数据、更新长期没动过的职位说明书, 该问什么、问谁。
- **方法论的使用**: 按维度访谈现任者 + 直属上级(两视角交叉验证): 工作介绍 → 主要职责 → 绩效标准/成功定义 → 权限与问责 → 所需知识 → 技能/经验 → 工作条件。
- **结论**: 产出应聚焦 essential functions (不能省的职能), 而非日常琐事, 以便后续用于 ADA 便利、招聘与绩效标准。
- **结果**: 这套访谈成为职位描述/招聘/ADA 依据的标准采集工具。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 写/更新职位描述或岗位说明书, 用户问"这个岗位到底要什么、怎么写才不悬空"。
2. 全新岗位没有任何参考人(如 AI 运维工程师), 用户问"从哪开始定义职责"。
3. 员工以残疾/宗教/医疗理由请求调整工作(工位、班次、职责), 用户问"怎么处理才合法、能不能拒绝"。
4. 有人质疑"哪些职责是核心的", 用户需要能举证的核心职能清单(应对合规审查)。
5. 用户纠结"职位描述按现人写还是按岗写"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **做职位分析 (先于人)**
   - 完成标准: 用职位分析访谈问题样张, 从现任者 + 直属上级两视角收集数据(也可辅以观察/问卷/组织图), 产出该岗位的活动与职责清单、工作条件、所需 KSA。

2. **界定并写出 essential functions, 产出/更新职位描述**
   - 完成标准: 区分核心职能与边缘职能; 每条核心职能都能回答"去掉此职能是否损害组织"(可举证); 职位描述按岗写、不按人写, 并同步产出任职资格。
   - 判停条件: 若这一步是为招聘准备的, 核心职能定稿后把 JD 交给 `recruiting-and-hiring`; 若收到合理便利请求则进入步骤 3。

3. **处理合理便利请求 (逐案互动流程)**
   - 完成标准: 记录所有请求 → 对照 essential functions 与个人资质 → 识别妨碍绩效的障碍 → 与员工互动确认能力与局限 → 评估各方案(有效性/成本/对环境与时效的影响/资源) → 选择并全程文档化; 不必采用员工首选方案, 也不得删除核心职能或降低标准。
   - 判停条件: 若确需以 undue hardship 拒绝, 必须相对企业规模逐案权衡(小企业更易主张, 大企业很难拿成本当挡箭牌)并文档化; 若已涉诉讼, 停止并移交律师。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已进入诉讼/仲裁的 ADA 个案: 需要律师实时处理, 不是流程模板能解决的。
- 非美国法域: ADA 是美国联邦法, 其他法域的残疾/便利规则不同。
- 招聘执行阶段(面试问题、背调、offer): 那是 recruiting skill 的领地, 本 skill 只负责把岗位与便利定义清楚。

### 常见失败模式

- **合理便利不得删除核心职能或降低标准**: essential functions 不是"平时做的事", 是"不能省的职能"; 用"去掉它是否损害组织"识别。
- **无视便利请求即可诉**: 所有请求必须被考虑, 逐案评估、文档化; "忽略或未加正当考虑即拒绝"本身构成歧视行为。
- **分析的是职位不是人**: 数据从在职者收集, 但不能把"某人做了什么"当成"职位要求什么"。
- **每条核心职能断言都要能举证**: 会被联邦合规机构审查, 不能事后为迁就个别员工降低/删减正当标准。

### 方法论局限 / 适用边界

- ADA 是联邦法, 方法对各州差异与法规修订未展开, 细节有保质期。
- 预设存在成型 HR 部门与文档体系; 中小团队做职位分析需自建轻量流程。
- 雇主视角: 便利决策中的互动是"雇主-员工"协商, 未充分讨论员工议价能力不对等。
- 方法中"mitigating measures"(判定残疾时不考虑助听器/药物等缓解措施, 普通眼镜除外)这类细节容易被跳过, 而它正是反直觉、决定保护范围的关键。

### 容易混淆的邻近方法论

- 与 `employment-law-basics` 的歧视双理论: 便利拒绝被控歧视时要回到双理论自检, 但便利流程本身是本 skill。
- 与 `compensation-and-pay-equity` 的 job evaluation: 都用"职位"为对象, 但一个是定岗定责/ADA, 一个是定级定薪。

## 快速理解: 5 个示例问题

用这 5 个最常被问到的场景快速上手本 skill, 每个问题都对应它真正触发的处理动作:

1. **这个新岗位没有任何参考人 (AI 运维工程师), 怎么定义它的职责?** — 从零职位分析 → KSA → 职位描述
2. **员工说腰痛, 要求只做轻活, 合理便利必须满足吗?** — 界定 essential functions → 逐案互动
3. **怎么判断哪些职责是核心职能, 哪些可以外包掉?** — 去掉此职能是否损害组织
4. **职位描述该按现任者的做法写, 还是按岗位本身要求写?** — 分析职位而非任职者
5. **员工以宗教理由要求每周五下午请假做礼拜, 我们周五人手最紧。** — 宗教便利: 逐案互动 + undue hardship
